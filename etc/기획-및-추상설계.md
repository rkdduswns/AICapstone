# ContextTrace 기획 및 추상설계

> **Windows 작업 로그 기반 개인 지식 출처 역추적 RAG 시스템**  
> 사용자가 과거에 실제로 무엇을, 언제, 어떤 프로그램에서 확인했는지를 찾아주는 Windows 기반 개인 지식 추적 시스템

---

## 1. 프로젝트 개요

ContextTrace는 Windows 환경에서 발생하는 사용자의 작업 맥락을 자동으로 수집하고 로컬에 축적한 뒤, 자연어 질의를 통해 과거에 열람한 정보의 **원본 출처, 열람 시각, 사용 프로그램, 관련 내용**을 다시 찾을 수 있도록 지원하는 시스템이다.

### 해결하려는 문제

| 문제 | 기존 방식의 한계 |
|---|---|
| 내용은 기억나지만 출처를 찾기 어려움 | 파일명이나 URL을 정확히 기억해야 함 |
| 브라우저 기록만으로 내용 검색이 어려움 | 방문 기록은 URL 중심으로 구성됨 |
| PDF, 문서, IDE 등의 작업 기록이 분산됨 | 애플리케이션 간 작업 맥락이 연결되지 않음 |
| 북마크·태그를 직접 남겨야 함 | 사용자의 추가 행동이 필요함 |
| 생성형 AI의 답변과 실제 열람 기록이 분리됨 | 사용자가 실제로 본 정보인지 확인하기 어려움 |

ContextTrace는 별도의 저장 동작 없이 **작업 이력을 자동 기록하고, 실제 열람 기록을 근거로 과거 자료의 출처를 역추적**하는 것을 핵심 가치로 한다.

---

## 2. 핵심 목표

| 목표 | 설명 |
|---|---|
| **자동 기록** | 별도의 북마크·저장·태깅 없이 작업 맥락을 수집 |
| **통합 추적** | 웹, PDF, 문서, IDE, 클립보드 기록을 하나의 작업 이력으로 관리 |
| **자연어 검색** | 정확한 파일명이나 URL을 몰라도 내용·시간·프로그램 조건으로 검색 |
| **출처 중심 응답** | 답변과 함께 URL, 파일 경로, 열람 시각, 프로그램 정보를 제공 |
| **로컬 우선 관리** | 작업 기록과 검색용 데이터를 기본적으로 사용자 PC 내부에 저장 |
| **근거 부족 응답 제한** | 충분한 기록이 없으면 존재하지 않는 출처를 임의로 생성하지 않음 |

## 4. 핵심 사용자 시나리오

### 4.1 웹페이지 역추적

사용자가 며칠 전 Chrome에서 SaaS 관련 보고서를 읽는다. 시스템은 페이지 제목, URL, 사용 프로그램, 열람 시각, 활성 시간 등의 정보를 자동 기록한다.

이후 사용자가 다음과 같이 검색한다.

> 지난주 Chrome에서 읽었던 SaaS 수익 모델 관련 자료 찾아줘.

시스템은 **시간 조건 + 프로그램 조건 + 의미 검색**을 결합하여 관련 웹페이지를 찾고, URL과 열람 시각을 반환한다.

### 4.2 PDF 역추적

사용자가 PDF 문서를 읽었지만 파일명을 기억하지 못하는 경우 다음과 같이 검색한다.

> NRR이 SaaS 성장 지표라고 설명한 PDF가 뭐였지?

시스템은 저장된 문서 내용에서 의미적으로 관련된 부분을 찾고, 해당 내용과 연결된 **원본 파일명, 파일 경로, 열람 시각**을 반환한다.

### 4.3 관련 작업 맥락 확인

특정 자료를 확인할 당시 함께 참고했던 다른 자료가 필요한 경우 다음과 같이 검색한다.

> LangGraph 조사할 때 같이 봤던 자료 보여줘.

시스템은 시간적으로 인접한 작업 기록을 바탕으로 웹페이지, PDF, 코드 파일 등의 관련 작업 이력을 하나의 세션으로 제시한다.

### 4.4 민감 정보 기록 차단

사용자가 차단 목록에 등록한 메신저, 금융 사이트, 비밀번호 관리 프로그램을 사용하는 경우 해당 작업 정보는 저장하지 않는다.

## 6. 작업 맥락 수집

백그라운드에서 현재 사용자가 실제로 보고 있는 작업 대상을 감지하고 필요한 정보를 수집한다.

### 수집 정보

| 항목 | 설명 |
|---|---|
| 프로그램 | Chrome, Edge, Word, VS Code 등 |
| 프로세스 | 현재 작업과 연결된 실행 프로세스 |
| 창 제목 | 웹페이지 제목, 문서명, 파일명 |
| URL | 브라우저에서 열람 중인 페이지 주소 |
| 파일 경로 | 로컬 문서의 원본 경로 |
| 클립보드 텍스트 | 사용자가 복사한 텍스트 |
| 시작 시각 | 해당 작업이 활성화된 시점 |
| 마지막 활성 시각 | 마지막으로 확인된 활성 시점 |
| 활성 시간 | 전면 활성 상태였던 누적 시간 |
| 재방문 횟수 | 동일 작업이 다시 전면에 나타난 횟수 |

### 수집 흐름

```text
활성 창 감지
  → 프로세스 식별
  → 창 제목 확인
  → URL / 파일 정보 확보
  → 개인정보 보호 검사
  → 작업 기록 생성 또는 갱신
```

### 수집 구조

```text
작업 맥락 수집
├─ 창 정보
├─ 브라우저 정보
├─ 파일 정보
├─ 클립보드 정보
└─ 프로그램별 추가 정보
```

프로그램마다 얻을 수 있는 정보와 접근 방식이 다르기 때문에 수집 기능은 서로 독립된 단위로 구성한다.

## 7. 활성 시간 및 재방문 추적

단순히 창이 한 번 열렸다는 사실만으로는 사용자가 해당 자료를 실제로 활용했는지 판단하기 어렵다. 따라서 활성 시간과 재방문 여부를 함께 기록한다.

```text
opened_at
last_active_at
active_duration
foreground_count
```

예:

```text
Chrome - SaaS Metrics Report
13:21:00 ~ 13:26:32
활성 시간: 332초
재방문 횟수: 2회
```

이 정보는 검색 결과에서 사용자가 실제로 오래 확인했거나 반복적으로 참고한 자료를 구분하는 보조 신호로 활용한다.

## 8. 작업 맥락 전처리

수집된 원시 기록은 그대로 검색에 사용하지 않고 검색 가능한 형태로 정리한다.

```text
원시 작업 기록
  → 중복 제거
  → 텍스트 정제
  → 문서 분할
  → 작업 세션 구성
  → 의미 표현 생성
  → 검색 색인
```

### 중복 기록 병합

동일한 창이 짧은 주기로 반복 감지되면 여러 개의 독립 기록을 생성하지 않고 하나의 연속 작업으로 병합한다.

```text
13:20 SaaS Report
13:20 SaaS Report
13:21 SaaS Report
13:21 SaaS Report
```

↓ 병합

```text
SaaS Report
13:20 ~ 13:21
활성 시간: 92초
```

### 문서 분할

긴 웹 문서나 PDF·Word 문서는 내용 전체를 하나의 검색 단위로 사용하지 않고 여러 텍스트 조각으로 나눈다.

```text
원본 문서
├─ 문서 조각 1
├─ 문서 조각 2
├─ 문서 조각 3
└─ 문서 조각 4
```

각 문서 조각은 반드시 원본 작업 기록과 연결되어야 하며, 검색 결과에서 다시 실제 URL이나 파일 경로로 역추적할 수 있어야 한다.

---

## 9. 혼합 검색

ContextTrace는 의미 유사도만 사용하는 검색이 아니라 **시간, 프로그램, 파일 종류 등의 조건과 의미 검색을 함께 사용하는 혼합 검색**을 기본 구조로 한다.

예:

> 지난주에 Chrome에서 읽었던 B2B SaaS 수익 모델 자료 찾아줘.

| 질의 표현 | 검색 조건 |
|---|---|
| 지난주 | 시간 범위 |
| Chrome | 프로그램 |
| B2B SaaS 수익 모델 | 내용 의미 |

### 검색 흐름

```text
사용자 질의
  → 시간 / 프로그램 / 파일 조건 분석
  → 조건에 맞는 작업 기록 후보 추출
  → 내용 의미 검색
  → 검색 결과 재정렬
  → 상위 결과 반환
```

### 검색 결과 재정렬에 활용할 정보

- 내용 의미 유사도
- 사용자가 지정한 시간 범위와의 일치
- 프로그램 및 파일 종류 일치
- 최근 열람 여부
- 활성 시간
- 재방문 횟수

각 요소의 실제 반영 비율은 고정하지 않고 검색 품질을 확인하면서 조정한다.

## 10. 근거 기반 RAG

검색 결과는 LLM이 답변을 생성할 때 사용할 **근거 데이터**로 전달한다. LLM의 일반 지식만으로 출처를 생성하는 것이 아니라, 실제 작업 이력에서 검색된 정보가 답변의 기준이 되어야 한다.

```text
사용자 질문
  → 혼합 검색
  → 관련 작업 기록
  → 답변 근거 구성
  → 응답 생성
  → 답변 + 출처 반환
```

### 응답 정보

| 항목 | 예시 |
|---|---|
| 문서명 | SaaS Metrics Report |
| 출처 | URL 또는 파일 경로 |
| 열람 시간 | 2026-09-10 14:22 ~ 14:27 |
| 프로그램 | Google Chrome |
| 관련 내용 | NRR과 CAC Payback Period 관련 내용 |
| 관련 세션 | SaaS BM 조사 |

### 근거 부족 처리

```text
검색 결과가 충분함
→ 검색된 기록을 근거로 응답

검색 결과가 부족함
→ 충분한 기록을 찾지 못했음을 안내
```

예:

> 해당 내용을 열람했다는 충분한 기록을 찾지 못했습니다.

시스템에 존재하지 않는 URL, 파일명, 열람 기록을 임의로 만들어내지 않는 것을 기본 원칙으로 한다.

## 11. 작업 세션 구성

개별 작업 기록을 시간 순서의 파편으로만 저장하지 않고, 서로 연관된 작업들을 하나의 세션으로 묶는다.

예:

```text
13:10  Chrome    OpenAI Agents
13:20  Acrobat   Agent Survey.pdf
13:35  VS Code   rag.py
13:48  Chrome    LangGraph Documentation
```

↓ 작업 세션

```text
AI Agent 구현 조사
13:10 ~ 14:02

관련 자료
- OpenAI Agents
- Agent Survey.pdf
- rag.py
- LangGraph Documentation
```

초기에는 **시간적 인접성**을 중심으로 세션을 구성하고, 필요한 경우 이후 내용 유사도나 반복적인 창 전환 관계를 보조적으로 활용한다.

## 13. 데이터 흐름

### 작업 기록 생성

```text
활성 작업 감지
  → 작업 정보 수집
  → 개인정보 보호 검사
  → 기존 기록과 중복 여부 확인
  → 작업 기록 생성 또는 갱신
  → 메타데이터 저장
```

### 문서 내용 색인

```text
웹 / 파일의 텍스트 확보
  → 텍스트 정제
  → 문서 분할
  → 의미 검색용 데이터 생성
  → 검색 데이터 저장
  → 원본 작업 기록과 연결
```

### 검색 및 응답

```text
자연어 질의
  → 시간 / 프로그램 / 파일 조건 분석
  → 작업 기록 후보 검색
  → 내용 의미 검색
  → 결과 재정렬
  → 근거 선택
  → RAG 응답 생성
  → 답변 + 실제 출처 반환
```

## 14. 추상 데이터 모델

### 작업 기록

사용자가 특정 프로그램이나 자료를 실제로 확인한 하나의 작업 단위이다.

```text
ContextRecord
├─ id
├─ application
├─ process
├─ window_title
├─ url
├─ file_path
├─ opened_at
├─ last_active_at
├─ active_duration
├─ foreground_count
├─ clipboard_text
└─ session_id
```

### 문서 조각

긴 문서에서 검색에 사용되는 내용 단위이다.

```text
DocumentChunk
├─ id
├─ context_id
├─ chunk_index
├─ text
└─ semantic_data_id
```

### 작업 세션

연관된 여러 작업 기록을 하나로 묶은 상위 단위이다.

```text
WorkSession
├─ id
├─ started_at
├─ ended_at
├─ title
└─ summary
```

### 출처 연결 관계

```text
검색된 문서 조각
  → 원본 작업 기록
  → URL / 파일 경로
  → 열람 시각
  → 작업 세션
```

검색을 위해 분리된 데이터가 원본 출처와 분리되지 않도록 모든 검색 결과는 실제 작업 기록으로 역추적 가능해야 한다.

## 15. 개인정보 보호

개인정보 보호는 부가 기능이 아니라 **수집 및 저장 과정에 반드시 포함되는 기본 처리 단계**로 정의한다.

### 기본 흐름

```text
작업 정보 수집
  → 개인정보 보호 검사
  → 저장 허용 여부 결정
  → 허용된 데이터만 저장
```

### 프로그램 차단

사용자가 지정한 프로그램이 활성화된 경우 해당 작업 기록을 생성하지 않는다.

예:

- 비밀번호 관리자
- 메신저
- 금융 프로그램
- 사내 보안 프로그램
- 사용자가 직접 지정한 프로그램

### URL 차단

특정 웹사이트에서는 작업 기록을 저장하지 않는다.

지원 범위:

- 정확한 URL 일치
- 도메인 단위 차단
- 하위 경로를 포함한 패턴 기반 차단

### 민감 텍스트 필터

클립보드나 문서 내용에서 민감한 문자열이 감지된 경우 해당 내용을 저장하지 않거나 필요한 경우 일부를 제거한다.

탐지 대상 예:

- OTP
- API Key
- Access Token
- 카드 번호
- 주민등록번호 형태
- 사용자 지정 문자열 패턴

### 기록 일시정지

사용자는 언제든지 전체 작업 기록 수집을 일시정지하고 다시 시작할 수 있어야 한다.

### 로컬 우선 관리

작업 기록과 검색용 데이터는 기본적으로 사용자 PC 내부에서 관리한다.

함께 고려할 항목:

- 저장 데이터 접근 제한
- 기록 삭제
- 전체 기록 초기화
- 데이터 보존 기간 설정
- 필요한 경우 저장 데이터 암호화

### 외부 LLM 사용 시

외부 LLM을 사용하는 경우 전체 작업 기록을 전달하지 않고, 검색 결과 중 답변에 필요한 일부 근거만 전달한다.

```text
로컬 검색
  → 필요한 근거 선택
  → 민감 정보 제거
  → 외부 LLM 전달
```

## 17. 초기 구현 완료 기준

초기 구현은 다음 조건을 모두 만족하면 핵심 흐름이 완성된 것으로 본다.

- [ ] Chrome 또는 Edge에서 열람한 웹페이지의 제목, URL, 열람 시간, 사용 프로그램, 활성 시간이 자동으로 기록된다.
- [ ] 사용자가 정확한 제목이나 URL을 몰라도 자연어로 과거 작업 기록을 검색할 수 있다.
- [ ] 시간과 프로그램 조건이 포함된 질의를 검색에 반영할 수 있다.
- [ ] 검색 결과에서 실제 URL 또는 파일 경로와 열람 시각을 확인할 수 있다.
- [ ] 검색된 내용과 원본 작업 기록 사이의 연결이 유지된다.
- [ ] 차단 프로그램 또는 차단 URL에서는 작업 정보가 저장되지 않는다.
- [ ] 사용자가 언제든지 전체 기록을 중지하고 다시 시작할 수 있다.
- [ ] 충분한 근거가 없는 경우 존재하지 않는 출처를 임의로 생성하지 않는다.

## 18. 프로젝트 차별점

### 브라우저 방문 기록과의 차이

```text
브라우저 방문 기록
→ 웹 URL 중심의 개별 방문 이력

ContextTrace
→ 웹 + 문서 + IDE + 클립보드 + 열람 시간 + 작업 맥락
```

브라우저 외부에서 이루어진 작업까지 하나의 지식 탐색 이력으로 연결한다는 점에서 차이가 있다.

### 일반적인 RAG와의 차이

```text
일반적인 RAG
사용자가 문서 제공
  → 문서 검색
  → 질의응답
```

```text
ContextTrace
실제 Windows 작업
  → 자동 작업 기록
  → 개인 작업 이력 구축
  → 자연어 검색
  → 실제 과거 출처 역추적
```

ContextTrace의 핵심은 일반적인 지식 질의응답이 아니라 **사용자가 실제로 확인했던 정보와 그 당시의 작업 맥락을 다시 복원하는 것**에 있다.
