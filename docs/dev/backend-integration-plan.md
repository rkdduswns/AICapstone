## 2. 통합에서 유지할 규칙

- Client는 HTTP 요청·응답과 표시를 담당한다. DB 마이그레이션, 개인정보 검사, 원문·검색 데이터 저장은 Backend가 담당한다. 브라우저 확장은 HTTP만 사용한다.
- `ContextRecord.id`는 실제 저장된 작업 기록 ID다. 가장 최근 작업, 비슷한 창 제목, URL 또는 시간으로 누락된 연결을 보충하지 않는다.
- 출처 ID, 작업 ID, 원본 URL·파일 경로, 작업 시각과 본문 수집 시각을 구분한다. 검색 청크와 답변 근거는 이 연결을 따라 원본 작업으로 돌아갈 수 있어야 한다.
- 수집을 허용하는 영속 정책을 읽은 뒤 수집기를 시작한다. 설정 읽기 실패·손상 시 허용 상태로 바꾸지 않는다. 설정 저장 실패 시 성공 응답이나 메모리 상태 변경을 먼저 하지 않는다.
- 거부한 본문은 원문 저장소·검색 청크·임베딩·LLM 입력에 들어가지 않는다. 저장 전 검사뿐 아니라 파생 자료 조회 시 현재 정책도 적용한다.
- 현재 지원 중인 API 경로·응답과 오래된 DB를 보존하면서 작은 단계로 합류한다. 전체 `app.py`·`ActivityStore` 교체를 통합 방법으로 사용하지 않는다.

프로젝트 표시명은 **강써치**다. 패키지·환경변수·저장 경로·서비스 식별자의 변경은 별도 호환성 작업이다. 이름 정리만으로 기존 토큰, DB 위치 또는 프로토콜을 바꾸지 않는다. Python 배포명은 `gangsearch`, 새 토큰 환경변수는 `GANGSEARCH_BROWSER_TOKEN`이다. 구형 `CONTEXTTRACE_BROWSER_TOKEN`은 새 변수가 없을 때 호환 수용한다. API v1 서비스명·헤더와 `.contexttrace/activity.db`는 유지한다. [이름 변경 결정](../reports/gangsearch-integration.md)을 따른다.

## 3. 수집 API 호환 설계안

이 절은 다음 구현의 제안이다. 경로는 기존 경로를 재사용한다. `ok/data/error` 응답 형식과 현재 Client가 검증하는 필드는 유지한다.

### 3.1 실제 작업 ID의 경계 어댑터

새 요청의 표준 이름을 `context_id`로 두고, 현재 Client·확장의 `record_id`를 호환 별칭으로 받는다. HTTP 경계에서 한 번 해석한 뒤 내부 저장 함수에는 하나의 실제 작업 ID만 전달한다.

| 입력 | 제안 동작 |
|---|---|
| `context_id`만 존재 | 실제 저장 작업을 확인하여 사용 |
| `record_id`만 존재 | 같은 의미의 호환 입력으로 처리 |
| 두 값이 같은 ID | 하나의 연결로 처리 |
| 두 값이 서로 다름 | 422, 출처·본문·청크를 쓰지 않음 |
| 둘 다 없음 | 현재의 연결 없는 수집 호환 유지; 작업 연결·검색 청크 생성 안 함 |
| 형식·범위 오류 | 422; 소수·불리언 등 잘못된 ID를 다른 작업 ID로 변환하지 않음 |
| 존재하지 않는 저장 작업 | 404, 새 출처를 쓰지 않음 |

JSON ID는 `ContextRecord.id`의 문자열 표현과 현재 숫자 입력을 모두 명시적으로 검사한다. 내부 SQLite ID는 1 이상 `2**63 - 1` 이하 정수로 제한한다. 숫자 문자열의 허용 형식과 두 별칭 비교를 공통 함수로 검증한다.

브라우저의 연결 요청은 기존의 “수집 중인 실제 Chrome/Edge 작업인가” 검사도 유지한다. 관측 후 작업이 바뀌거나 브라우저 종류가 다르면 409를 반환하며 다른 작업으로 재연결하지 않는다. 기존 URL 전환에 따른 작업 종료·새 작업 생성 처리를 보존한다. 이때 최종 연결 ID는 응답에 명시한 실제 저장 ID이며, 입력 ID를 무조건 되돌려주지 않는다.

### 3.2 `/browser/source`

제안 요청 예시는 다음과 같다. `context_id`는 임의 값이 아니라 `/activity/current`에서 확인한 실제 저장 ID다.

```json
{
  "browser": "chrome",
  "url": "https://example.com/research",
  "page_title": "Research page",
  "context_id": "123"
}
```

현재 확장의 `record_id` 전송도 같은 어댑터로 받는다. 현재 서버의 응답 필드 `id`, `browser`, `url`, `page_title`, `captured_at`, `activity_record_id`를 유지한다. `activity_record_id`는 현재 브라우저 응답처럼 문자열 또는 `null`이며, 연결 없는 수집에서 가짜 작업 ID를 반환하지 않는다. 새 응답 필드를 필수로 만들어 기존 Client를 깨뜨리지 않는다.

토큰 없이 Chrome 데이터를 받는 방식은 `c95b440`에서 구현된 것으로 확인되지 않았다. 현재 bearer 검사를 유지한다. 토큰 제거·자동 수집 인증 방식은 아래 합의 항목이 확정된 뒤 별도 단계로 진행한다.

### 3.3 `/browser/content`와 잘림 표시

```json
{
  "browser_source_id": 1,
  "content_text": "수집된 웹 본문",
  "truncated": true
}
```

- `truncated`는 선택 불리언이며 생략 시 `false`다. 문자열 `"false"` 등을 참으로 잘못 해석하지 않도록 요청 검증을 시험한다.
- 원본 브라우저 본문 행에 수집 시 잘림 여부를 저장한다. 같은 출처 본문을 갱신할 때 새 본문·수집 시각·잘림 표시를 함께 교체하고 이전 파생 청크·임베딩을 무효화한다.
- 상세 응답의 잘림 표시는 `수집 시 truncated OR 조회 표시 길이 초과`로 계산한다. 기존 서버는 50,000자 조회 제한에 걸린 경우만 표시하므로 이 차이를 수정한다.
- `SourceMetadata.content_truncated`에도 수집 단계의 상태를 전달한다. 조회용 본문을 잘라서 색인 원문으로 다시 저장하지 않는다.
- 이전 DB 행의 호환 기본값 `false`는 “수집 시 잘림 보고가 없었다”는 의미다. 이전 본문이 완전했다고 새로 보장하지 않는다.
- 수집 일시정지·민감 본문 거부는 403이다. 확장과 Client는 이를 저장 성공으로 처리하거나 자동으로 재전송하지 않는다. 기존 잘림 경고 UI는 실제 저장·상세 응답의 이 상태를 사용한다.

### 3.4 `/documents`의 ID·경로·보관 범위

제안 multipart 입력은 `file`, 선택 `context_id` 또는 호환 `record_id`, 원본 `file_path`다. ID가 있으면 현재와 같이 사용자가 명시한 실제 작업에만 연결하고 유효한 원본 Windows 경로를 검증한다. 연결 없는 업로드의 기존 호환 지원 여부를 바꾸려면 별도 결정과 Client 변경을 함께 한다.

현재 Client는 업로드 응답의 정수 또는 `null`인 `activity_record_id`가 요청한 작업과 같은지 확인한다. 연결된 문서에는 원본 `file_path`도 필요하다. 두 필드를 유지하고, 업로드 성공 응답만으로 다른 작업에 연결됐다고 표시하지 않는다. 목록·이력·상세 응답에서도 같은 경로 의미를 사용한다.

| 값 | 용도와 제안 소유권 |
|---|---|
| 원본 `file_path` | Client의 Windows 파일 경로; 원본 열기·출처 표시용 메타데이터; Backend가 이 입력 경로로 파일을 다시 열지 않음 |
| 서버 임시 파일 | 업로드 검사·본문 추출에만 사용; 성공·실패 모두 정리 |
| 서버 영구 복사 경로 | `c95b440`의 UUID 사본; 원본 경로와 다른 저장 필드로 구분해야 함 |

`c95b440`은 업로드 원본 파일을 영구 복사하지만 현재 연결된 업로드는 이를 하지 않는다. 원본 파일 영구 보관은 이번 호환 통합의 필수 작업이 아니다. 기본 통합안은 현재처럼 추출 후 임시 파일을 정리한다. 서버 사본 보관이 필요하다면 보관 목적·삭제 정책·민감 본문 차단 시 처리부터 합의하고, 별도 `stored_file_path` 등 서버 내부 필드로 도입한다. 사본만 있는 과거 행에서 원본 Windows 경로를 만들어내지 않는다.

본문 검사에 걸리면 403을 반환한다. 문서 행·연결·검색 자료·영구 사본을 남기지 않는다. 검사를 위해 생성한 임시 파일은 정리한다. 민감 본문 저장 동의, 사용자 메모·중요도는 합의 전이므로 이번 통합에서 추가하지 않는다.

## 4. DB·검색 자료 합류 설계안

### 4.1 기존 원본·링크를 먼저 보존

현재 구현은 `record_browser_sources`·`record_document_sources`로 작업과 출처를 연결한다. `c95b440`은 문서의 `context_id` 및 검색 출처의 `context_id`를 별도로 둔다. 먼저 현재 링크 테이블을 원본 연결의 기준으로 유지하고, 새 저장소에 넘기는 어댑터가 이 링크에서 실제 ID를 읽도록 한다.

직접 FK 구조로 전환하려면 실제 링크와의 동일성·다중 연결 처리 규칙을 먼저 검사해야 한다. 제목·시각 기반 역추정은 하지 않는다. 링크가 없거나 서로 충돌하면 그 출처는 검색에서 제외하고 원본은 보존한다. 두 저장 경로가 각자 연결을 갱신하는 상태로 운영하지 않는다.

### 4.2 같은 `search_chunks` 이름의 충돌

| 로컬 `d274643` | Backend `c95b440` |
|---|---|
| `record_id`와 브라우저/문서 출처 FK가 청크 행에 있음 | `search_source_id`를 통해 출처·작업을 참조 |
| 본문 갱신·영속 보호 설정 변경 시 삭제 트리거 | 별도 `search_sources`·임베딩 테이블 사용 |
| 실제 원본 링크·수집 시각과 현재 정책으로 조회 재검사 | 공통 메타데이터 JSON과 청크·벡터 저장 함수 제공 |
| 출처별 정규화·최대 1,000자 청크, 같은 출처 안에서 중복 제거, 스냅샷 기준 ID | 기본 최대 50,000자 분할, 청크 UUID 생성 |

`CREATE TABLE IF NOT EXISTS search_chunks`로 두 스키마를 호환시킬 수 없다. 다음 검색 단계 전 두 DB 형태를 감지하는 버전 검사·명시적 마이그레이션을 넣는다. 모르는 형태는 색인 쓰기를 중단하고 오류를 보고한다. 기존 테이블을 자동 삭제하거나 같은 이름에 다른 의미의 행을 섞지 않는다.

제안 진행 방식은 현재 원본·링크를 유지한 채 **검색 저장 형식 하나만 선택**하는 것이다. `c95b440`의 `search_sources`·벡터 저장 형식을 채택하더라도 PR #19·#20·로컬 색인의 정책 검사, 출처 연결 검증, 본문 갱신·정책 변경 시 무효화 규칙을 함께 이식한다. 청크 길이·ID 규칙은 공통 계약으로 확정한 뒤 한 생성기만 호출한다. `document_chunks`와 `search_chunks` 양쪽에 같은 문서를 독립적으로 색인하지 않는다.

### 4.3 마이그레이션과 파생 자료 수명

1. 별도 사본 DB에서 현재 Client DB, `c95b440` DB, 빈 DB를 각각 입력으로 시험한다. 원본 행 수·ID·링크·시각·경로를 전후 비교하고 `foreign_key_check`를 수행한다.
2. 보호 설정을 먼저 복원하고 수집 시작 전에 적용한다. 손상된 정책을 새 기본값으로 덮어쓰면서 색인하지 않는다.
3. `browser_content_records`에 선택 필드의 호환 저장 열을 추가한다. 기존 자료를 가장 최근 작업에 연결하는 마이그레이션은 만들지 않는다.
4. 명시적 링크와 허용 정책을 통과한 출처만 다시 정규화·청크 생성한다. 파생 색인은 재생성할 수 있지만 원본 자료는 삭제하지 않는다.
5. 원문 수정·출처/작업 삭제·보호 설정 변경에서 관련 청크와 벡터를 같은 트랜잭션으로 삭제하거나 조회 불가능하게 만든다. 조회도 현재 원본 링크와 정책을 확인한다.
6. 청크 ID가 바뀌면 이전 벡터를 재사용하지 않는다. 벡터에는 실제 청크 ID, 모델명, 차원을 연결한다. 재시도·중단 후 재실행에서 중복 색인과 고아 벡터가 생기지 않아야 한다.

`c95b440`의 E5 서비스는 최초 사용 때 모델을 불러오며 384차원·정규화·유한 수를 검사한다. 이는 HTTP 검색이나 실제 모델 다운로드·실행 검증 완료를 뜻하지 않는다. 기본 서버 시작·Client 실행·문서 수집이 모델 설치·다운로드 성공에 의존하지 않게 유지한다.

## 5. 작은 phase와 우선순위

각 단계는 독립 PR로 검토할 수 있다. 이미 완료된 단계는 다시 구현하지 않고 해당 커밋의 실제 테스트와 현재 기준 브랜치 충돌만 확인한다.

### P0-A — 영속 보호 설정·최근 이력 정렬 기반 합류

2026-11-13 통합 작업 브랜치에 PR #17·#18과 PR #19·#20의 읽기 전용 준비까지 합류했다. 아래 기준을 이번 전체 회귀 검증에 적용한다. main 최종 결과는 [통합 검증](../reports/gangsearch-integration.md)을 따른다.

- **목적·범위:** PR #17·#18의 현재 구현을 통합 기준에 반영하여 저장/복원과 수집 시작 순서, 정렬 후 제한을 고정한다. 검색·UI 신규 기능은 추가하지 않는다.
- **선행조건:** 현재 연결된 서버와 PR 두 개의 차이 및 누적 관계를 확인한다.
- **구현:** 확인된 변경만 병합 또는 충돌 해결한다. 기존 Client용 경로와 본문 403 검사를 유지한다.
- **검증:** 재시작 시 일시정지·차단 설정 복원, 손상/저장 실패 시 닫힌 처리, 설정 변경과 동시 수집, 서로 다른 시간대·동일 시각·`LIMIT` 경계의 정렬 회귀 시험.
- **완료조건:** 현재 Client 테스트와 해당 Backend 시험이 함께 통과하며, 설정 복원 전에 새 수집이 시작되지 않는다. 이후 단계가 미완료라는 이유로 이 단계 자체를 미완료로 두지 않는다.

### P0-B — 수집 계약 어댑터와 잘림 상태 연결: 다음 최소 신규 phase

- **목적:** 동업자가 전달한 두 선택 필드와 거부 응답을 실제 현재 저장·조회 경계에 맞춘다.
- **선행조건:** P0-A의 보호 설정과 현재 Client용 서버를 기준으로 삼는다. 문서 원본 영구 보관은 이 단계에서 도입하지 않는다.
- **구현 항목:** `context_id`/`record_id` 검증 어댑터, 실제 작업 연결, `truncated` 요청 검증·DB 저장·상세/검색 메타데이터 전달, 기존 403 유지, 업로드 응답의 연결 ID·원본 경로 보존. 기존 Client와 확장을 당장 동시에 배포해야 하는 변경을 피한다.
- **검증:** ID 생략/각 별칭/동일·충돌 별칭/없는 ID/다른 브라우저/만료 작업을 시험한다. 잘림 `true`·`false`·생략·잘못된 타입, 50,000자 이하에서 이미 잘린 본문, 조회 제한만 넘는 본문, 본문 갱신을 시험한다. 두 저장 경로의 민감 본문과 일시정지 403에서 원문·링크·파생 자료가 늘지 않고 Client가 성공으로 표시하지 않는지 확인한다. 이전 DB에 적용 후 재시작하고 이전 Client 요청도 시험한다.
- **완료조건:** 실제 Client/확장 요청→서버 저장→상세 조회 한 번의 흐름에서 ID와 잘림 표시가 보존된다. 기존 테스트와 새 경계 시험이 통과한다.
- **중단조건:** 출처 연결이 유일하게 해석되지 않거나 원본 경로/사본 경로를 구별할 수 없으면 해당 연결·색인만 중단한다. 추정 연결·원본 삭제로 진행하지 않는다. 문서 업로드 필수 ID 전환 또는 원본 사본 보관을 새로 요구하는 변경은 아래 합의가 필요하다.

### P1-A — 출처 검증·청크·색인 저장 한 경로로 합류

- **목적·범위:** PR #19·#20과 `d274643`, `c95b440`의 저장 기능을 단일 생성·저장 경로로 정리한다. 검색 HTTP·LLM은 범위 밖이다.
- **선행조건:** P0-B 완료, 청크 규칙·DB 형식 선택, 출처 연결 어댑터와 정책 영속화.
- **구현:** 명시적 스키마 감지/이관, 정규화·분할 재사용, 정확한 원본 작업·출처·수집 시각 저장, 변경/삭제/정책 전환 시 무효화. CLI로 명시한 작업만 갱신하는 기존 통제 범위를 유지한다.
- **검증:** 세 DB 형태의 이관·재실행, 한 출처 내 중복 제거와 서로 다른 작업 간 출처 보존, 미연결/거부 자료 제외, 정책 변경·본문 교체·원본 삭제·중간 실패 후 재실행. 원본 불변과 고아 청크 0건 확인.
- **완료조건:** 같은 원본·정책에서 동등한 출처 스냅샷을 읽으며, 다른 스키마를 조용히 수용하지 않는다. 정책 변경 후 이전 검색 자료가 노출되지 않는다.

### P1-B — 기존 조건 검색 HTTP 연결

- **목적·범위:** 이미 정의한 [조건 검색 계약](search-api.md)의 `GET /records/search`를 실제 저장소에 연결한다. 제목·프로세스·출처·시간 조건의 기록 검색이며 임베딩 검색과 구별한다.
- **선행조건:** 기록 출처 투영과 P0-A의 안정 정렬. 본문·벡터가 필요 없는 이 API는 P1-A의 모델 설치를 선행조건으로 만들지 않는다.
- **구현:** 기존 문서의 요청 정규화·요청 echo, AND 조건, 시간 구간·정렬·동일 시각 ID 순서, `limit`·`has_more`, `ContextRecord` 응답을 구현한다. 기존 계약과 다른 임의 응답을 만들지 않는다.
- **검증:** 실제 SQLite→HTTP→현재 Client 파서 경로, 조건 경계와 동시 갱신, 잘못된 요청·403·서버 미지원 처리, 응답 ID/정렬/출처 검증.
- **완료조건:** 가짜 서버 없이 조건 검색이 동작하고 현재 Client 계약 시험이 실제 서버에 통과한다.

### P2-A — 임베딩 저장·실제 검색 계약 확정

- **목적·범위:** 채택한 청크에만 E5 임베딩을 연결하고 의미 검색 API를 설계·구현한다. 현재 존재하는 HTTP 기능으로 표시하지 않는다.
- **선행조건:** P1-A, 모델 사용·설치 방식과 API 계약 합의.
- **구현:** 모델명·차원·청크 ID 검증, 재색인/모델 변경 시 벡터 무효화, 실패해도 기본 수집·이력 유지. 실제 API 경로·점수 의미·필터/정렬 상호작용·페이지 제한은 구현 전 문서화한다.
- **검증·완료조건:** 가짜 벡터 계약 시험과 별도 실제 모델 시험을 구분하고 기록한다. 삭제·정책 변경 이후 결과 제외, 누락/오류 모델 상태, 기존 Client 검색 경계와의 통합을 확인해야 의미 검색 완료로 처리한다.

### P2-B — LLM 답변·근거 연결

- **목적·범위:** 가짜 답변 제공자를 실제 Backend 답변으로 교체한다.
- **선행조건:** 허용된 검색 결과와 모델/외부 전송 정책, 답변 응답 계약 합의.
- **제안 응답 정보:** 답변 텍스트와 별도 근거 목록. 각 근거에는 화면 참조 번호, 실제 `context_id`, 청크 ID, 원본 출처, 수집 시각, 잘림 여부를 연결한다. 이는 필드명까지 확정한 현재 API가 아니다.
- **검증·완료조건:** 답변의 `[N]` 참조가 반환된 실제 근거에만 매핑되고, 정렬·드롭다운 선택·복사 후에도 같은 근거를 가리킨다. 근거 없는 문장을 임의로 특정 출처에 강조하지 않는다. 민감정보·정책 변경·본문 잘림을 반영하고, 모델 실패·취소 후 기본 검색을 사용할 수 있어야 한다.

## 7. main 반영 판단과 실제 재검증

`69473fe`의 연결된 Client/server는 별도 Backend의 모든 검색 단계가 끝나야만 병합 가능한 구조가 아니다. 문서·표시명 변경, 검증된 Client 기능, 개별 보호/정렬 보완은 현재 변경 묶음의 테스트와 검토가 통과하면 각각 main 후보가 된다. 반면 `c95b440`의 앱·저장소 전체 교체와 서로 다른 검색 스키마는 위 호환·이관 시험 전 전체 병합 후보로 보지 않는다.
