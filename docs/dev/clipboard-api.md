# Phase 6 클립보드 설정 및 저장 텍스트 조회

상태: Client/Shared 및 가상 HTTP 검증 범위. 실제 클립보드 감지·작업 연결·필터·중복 방지·저장은 Backend 연결 후 검증한다.
Client는 OS 클립보드를 직접 읽거나 감시하지 않는다. 이미 저장되어 Backend가 제공한 텍스트만 표시한다.

## 기록 사용 여부 설정

[개인정보 API](privacy-api.md)의 `settings`에 선택 필드 `clipboard_enabled`를 추가한다.

| 값 | 의미 / Client |
|---|---|
| `true` | 클립보드 기록 사용 설정 켜짐 |
| `false` | 클립보드 기록 사용 설정 꺼짐 |
| 누락 또는 `null` | 구형 Backend의 기능 미지원. 변경 버튼 비활성화 |
| 그 밖의 타입 | 호환되지 않는 개인정보 응답 |

신규 Backend는 이 기능의 **초기 설정을 false**로 제공하고 명시적인 사용자 설정으로만 켠다.
필드가 없는 기존 응답을 false로 추측하지 않는다. 기존 Phase 5 Client는 추가 필드를 무시할 수 있다.

```http
PUT /privacy/clipboard
Content-Type: application/json
X-ContextTrace-Client: desktop

{"clipboard_enabled": true}
```

- 요청은 boolean 목표값만 전달한다. 전체 일시정지나 프로그램 차단 목록을 변경하지 않는다.
- 응답은 기존 개인정보 API의 HTTP 200 정상 envelope와 **적용된 전체 상태**다.
- 요청한 값이 응답에 확인되어야 켜짐/꺼짐으로 표시한다. 실패 시 적용 여부 미확인으로 전환하고 GET으로 재확인한다.
- PUT을 자동 재전송하지 않는다. timeout/취소는 서버 변경을 되돌리는 동작이 아니다.
- `clipboard_enabled: true`는 수집 설정이며 저장 허가를 의미하지 않는다. 전체 일시정지·프로그램 차단·민감정보 검사가 우선한다.
- 꺼짐은 이후 클립보드 수집/저장 중단이며, 기존 저장 항목을 삭제하거나 조회에서 숨기는 기능은 아니다.
- `/privacy`의 `recording`은 기존 전체 작업 기록 판정이다. 클립보드 사용 설정과 별도로 표시한다.

## 작업별 저장 텍스트 조회

```http
GET /records/clipboard?record_id=sample-record&limit=20
Accept: application/json
```

Client는 선택 작업의 ID를 쿼리 값으로 URL 인코딩하고 최대 20건을 요청한다.
ID가 경로나 다른 쿼리 파라미터로 해석되지 않게 한다. 서버는 디코딩된 원래 ID로 조회한다.
Backend는 `record_id`를 필수 비어 있지 않은 문자열로, `limit`를 정수 1–20(기본 20)으로 검증한다.
입력 오류는 HTTP 422와 기존 오류 envelope다. 존재하지 않는 작업은 HTTP 404다.

정상 응답 예시의 내용은 모두 가상 데이터다.

```json
{
  "ok": true,
  "data": {
    "service": "contexttrace-backend",
    "api_version": 1,
    "record_id": "sample-record",
    "entries": [
      {"id": "sample-copy", "copied_at": "2026-10-08T10:10:00+09:00", "text": "가상 복사 텍스트\n두 번째 줄"}
    ],
    "has_more": false
  },
  "error": null
}
```

| 필드 | 규칙 |
|---|---|
| `ok`, `error`, `service`, `api_version` | 기존 성공 envelope. true/null/정확한 서비스/정수 1, 필수 |
| `record_id` | 필수. 요청한 작업 ID와 정확히 일치해야 함 |
| `entries` | 필수 배열, 요청 개수 이하. null 거부. 기존 작업에 항목이 없으면 빈 배열 |
| `entries[].id` | 공백만 있지 않은 문자열. 복사 이벤트의 안정적인 ID, 응답 내 중복 금지 |
| `entries[].copied_at` | 필수. Phase 3과 같은 시간대 포함 ISO 시각, PC 현지 표시 가능 범위 |
| `entries[].text` | 필수 문자열. 공백뿐인 값 거부. 최대 10,000 Unicode 코드 포인트. 원문 공백·줄바꿈 유지 |
| `has_more` | 필수 boolean. 선택 작업에 이번 응답보다 오래된 조회 가능 항목이 더 있는지 표시 |

Backend가 작업별로 복사 시각 내림차순, 같은 순간은 ID 오름차순으로 정렬한 후 개수를 제한한다.
Client도 수신한 항목을 같은 순서로 표시하되 Backend의 최근 항목 선택을 대신하지 않는다.
필수 필드 누락/타입 오류/다른 작업 ID/중복 ID/과도한 길이는 응답 전체 실패다. 추가 필드는 무시한다.
정상 응답은 HTTP 200 / `application/json`이다. 서비스·API 버전은 기존과 같다.

Shared 정의는 `src/shared/clipboard.py`의 `ClipboardEntry`, `RecordClipboard`, `RecordClipboardResponse`다.
기획의 `ContextRecord.clipboard_text` 관계를 **작업 하나에 여러 복사 이벤트**로 구체화한다.
기획 원문과 기존 최근 기록 응답은 유지하며, 본문은 작업 ID에 연결된 별도 상세 조회로 제공한다.
DB 스키마는 Backend가 결정한다.

## 화면과 오류

- `개인정보 보호` 탭에서 클립보드 기록 켜기/끄기를 요청한다. 입력 중인 차단 목록은 유지한다.
- `최근 기록`에서 작업을 고르고 상세의 `복사 텍스트` 탭을 열면 처음 조회한다.
- 복사 시각 목록에서 항목을 고르면 읽기 전용 일반 텍스트로 표시한다. HTML/링크로 실행하지 않는다.
- 최대 최근 20건을 표시하고 `has_more`가 true이면 이전 항목이 더 있음을 알린다. 페이지 이동은 이번 범위에 없다.
- 새로고침은 목록을 교체한다. 작업 변경·기록 목록 새로고침·재연결·종료 시 이전 본문/요청을 비운다.
- 요청 ID 검증과 취소를 함께 사용해 늦은 A 작업 응답이 B 작업에 표시되지 않게 한다.
- 빈 목록은 정상 결과다. 404(미구현 API 또는 삭제된 작업), 서버/연결 오류, timeout, 잘못된 응답은 조회 오류다.
- 실패 시 이전 본문을 남기지 않고 수동 새로고침으로 복구한다. Client가 본문을 파일/로그에 저장하지 않는다.
- 공통 HTTP 계층의 loopback 고정, 프록시 비활성화, 리다이렉트 거부, 3초 요청 제한을 유지한다.

## Backend 연결 후 완료 조건

1. 텍스트 변화만 감지하고, 복사 순간의 작업 ID와 시각을 함께 고정한다. 현재 작업이 없으면 임의로 연결하지 않는다.
2. 설정 꺼짐·일시정지·차단 프로그램·민감 문자열은 저장 전에 배제한다. 설정 변경을 진행 중 수집/저장과 동기화한다.
3. 최대 10,000자를 초과한 텍스트는 저장하지 않는다. 일부만 잘라 원문인 것처럼 제공하지 않는다.
4. 반복 알림/동일 텍스트 복사의 중복 정책을 문서화하고 검증한다. 서로 다른 작업의 유효한 복사를 전역 중복 처리로 잃지 않도록 한다.
5. 일반 복사, 반복 복사, 창 전환 직후 복사, 민감 문자열, 일시정지 중 복사를 실제 OS와 저장소로 검증한다.
6. 저장 이벤트 ID/복사 시각/작업 관계가 재조회에도 유지되는지, 이전 저장 항목이 설정 변경으로 사라지지 않는지 확인한다.
7. [개인정보 API](privacy-api.md)의 로컬 API 접근 제어와 저장 전 보호 원칙을 적용한다.

가상 미리보기와 Client 테스트는 실제 수집·중복 방지·필터 적용·영속 저장의 검증 근거가 아니다.
