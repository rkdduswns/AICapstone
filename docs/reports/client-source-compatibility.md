# Client 출처 호환 경계 보완

작업 기준: 2026-11-13 `main`·`client_dev`의 `7e0991e`. 작업 브랜치: `fix/client-source-compatibility`.
확인 당시 별도 Backend 작업 끝은 `c95b440`이다.

## 목적·범위·선행조건

현재 Client가 선택한 실제 작업과 원본 파일을 새 서버의 다른 저장 경로로 잘못 연결했다고 표시하지 않게 한다.
선행조건은 기존 문서 업로드·최근 기록·본문 상세 연결이다.
이번 실행 코드 변경은 `src/client/`뿐이며 Backend·DB·Shared·브라우저 확장·의존성·배포 설정은 변경하지 않는다.

## 확인한 계약과 구현

- `/browser/source`의 새 `context_id`와 `/browser/content` 전송은 브라우저 확장 책임이다. 데스크톱은 두 API를 호출하지 않는다.
  사용자가 전달한 계약은 문서 업로드 요청 변경 없음이므로 `/documents`의 multipart `file`·선택 `record_id`·`file_path`를 유지한다.
  서버 지원 여부를 추정해 `context_id`를 추가하거나 필드를 바꿔 자동 재업로드하지 않는다.
- 문서 연결 ID는 실제 선택 기록의 정규 양의 ASCII 십진 문자열이며 최대 `2**63 - 1`이다.
  앞자리 0·다른 타입·범위 초과를 파일 열기와 POST 전에 거부한다. 가장 최근 작업을 대신 선택하거나 ID를 변환하지 않는다.
- 요청의 원본 경로·파일 이름·작업 ID를 기억하고 업로드 응답과 대조한다.
  원본 경로는 기존 문서 상세 계약처럼 원문 그대로 비교하며, 서버 사본 경로를 원본으로 간주하지 않는다.
  응답 ID·원본 경로·파일 이름/유형이 누락되거나 다르면 업로드·연결 성공 신호를 내지 않는다.
  이 경우 서버 저장 여부가 불명확하므로 목록과 최근 기록 확인을 안내하고 POST를 자동 재전송하지 않는다.
- 기존 HTTP 403 거부 처리를 유지한다. 성공처럼 생긴 JSON도 HTTP 거부 상태보다 우선하지 않는다.
  404·422는 기능/연결/문서 검증 중 원인을 확정할 수 없으므로 텍스트 추출 실패 하나로 단정하지 않는다.
- `truncated`는 기존 서버 불리언을 그대로 따른다. 짧은 본문도 true이면 **전체 본문 중 일부만 제공되었습니다**로 안내한다.
  길이 제한의 발생 위치나 DB 원문 손실 여부를 Client가 추정하지 않는다.

## 검증·완료조건

검증은 기존 실제 서버 연동과 Client의 가상 HTTP 경계를 사용한다.
기존 multipart 형식, 잘못된 ID의 파일/네트워크 접근 없음, 응답 출처 불일치 시 성공 억제,
403 성공 억제·자동 재업로드 없음, 짧은 잘림 본문과 조회 제한 본문 표시를 확인한다.
완료조건은 이 회귀 검증 통과와 Client 외 실행 코드 변경 없음이다.

- Windows Python 3.14.7: 기존 웹·문서 본문/실제 서버 연동 관련 **96개 통과**, 새 업로드 호환 경계 **25개 통과**(각각 실행).
- 새 HTTP 시험은 기존 200/201·연결 없는 요청, SQLite ID 상한, 오류 입력의 파일/POST 없음, 다른 원본 경로/ID/이름/유형 응답 거부, 403 우선·POST 한 번을 확인했다.
- 짧은 수집 일부 본문과 50,000자 조회 제한 본문의 표시를 확인했다. 실제 Chrome/Edge 또는 Windows 사용자 조작 검증으로 간주하지 않는다.
- Ruff·공백 검사 통과. 최종 Python 3.11·3.12 전체 자동 검증과 실제 client_dev 반영은 해당 PR의 GitHub 검사·병합 기록을 따른다.

서버의 `context_id` 별칭 수용·수집 잘림 상태 영속화·검색 메타데이터 전달은 미구현 잔여로 유지한다.
전체 [Backend 통합 설계](../dev/backend-integration-plan.md)의 완료로 처리하지 않는다.
