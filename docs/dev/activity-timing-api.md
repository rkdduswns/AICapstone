# Phase 3 Client 시간 표시 계약

기준일: 2026-10-01. Client/Shared 구현. 실제 Backend 시간 추적은 미구현이다.
기존 `/activity/current`, API 버전 1 및 Phase 2 필드를 유지한다.

## 응답 확장

`data.timing`을 선택 객체로 추가한다.

```json
"timing": {
  "started_at": "2026-10-01T10:00:00+09:00",
  "active_duration_ms": 65000
}
```

- `started_at`: Backend가 해당 작업에 기록한 시작 순간. `YYYY-MM-DDTHH:MM:SS`에
  선택 소수초(1~6자리)와 필수 `Z` 또는 `±HH:MM` 시간대를 붙인다.
  유효한 달력 시각이어야 하며 PC 현지 시각으로 변환 가능한 범위만 허용한다.
- `active_duration_ms`: Backend가 계산한 해당 작업의 누적 활성 밀리초. 0 이상 정수.
  boolean, 실수, 문자열은 거부한다. 비활성 구간은 Backend에서 제외한다.
- `collecting`에서 객체 또는 null을 허용한다. 필드 누락/null은 기존 Backend 또는
  해당 작업 시간 정보 미제공으로 해석하고 두 시간 영역에 `시간 정보 없음`을 표시한다.
  누락과 0밀리초는 다르다.
- 비수집 상태는 `timing` 누락/null만 허용한다. 창 없는 상태의 시간 객체는 거부한다.
- 객체가 제공되면 두 필드 모두 필수다. 잘못된 시간은 응답 전체를 거부하고 창/시간을
  비운 뒤 기존 자동 재시도로 복구한다. 추가 객체 필드는 무시한다.

## 화면 및 책임

시작 시각은 PC 현지 시각과 UTC 오프셋을 함께 표시한다. 마지막 정상 수신 시각과 별개다.
활성 시간은 밀리초 이하를 버려 `HH:MM:SS`로 표시하며 24시간 이후에도 시간이 누적된다.
Client는 로컬 타이머나 현재 시각에서 시작 시각을 빼는 방식으로 값을 추정하지 않는다.
동일 값 반복 수신 시 활성 시간이 늘어나지 않는다. 창 전환/재방문 시 최신 서버 값을 그대로
표시한다. 작업 동일성·재방문·누적 정책은 Backend 책임이다.

오류, 창 없음, 재확인 시 두 시간 영역을 즉시 비운다. 다음 정상 응답에서 복구한다.
폴링 간격, timeout, 종료 취소 및 동일 제목의 선택/스크롤 보존은 Phase 2 규칙을 유지한다.

Backend 구현 시 `src/shared/activity.py`의 `ActivityTiming`을 사용한다.
이 확장은 기존 Phase 2 Client가 추가 필드를 무시하는 규칙과 호환된다.
Backend 브랜치에는 아직 적용하지 않았으므로 통합 전에 규격과 Shared 정의를 반영해야 한다.
실제 Backend 시간 일치·1분 유지·A→B→A 계산·빠른 전환 병합은 후속 통합 검증이다.
