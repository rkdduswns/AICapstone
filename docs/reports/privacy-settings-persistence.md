# 개인정보 설정 영속화 검증

작업일: 2026-11-05 (KST). 브랜치: `feat/privacy-settings-persistence`.
선행조건: PR #16의 설정 API·정책·수집기·SQLite 연결.
기준 커밋: `b12a82a69b842060c43b991fe1524e027f899126`.
확인한 main: `7c307987182c629965da63824b60d36e41db4036`.

## 목적과 범위

Backend 재실행으로 사용자의 보호 선택이 초기화되는 문제를 해결한다.
현재 지원하는 `paused`, `blocked_processes`, `clipboard_enabled`만 기존 DB에 저장한다.
API·Client 화면 형식은 유지하고 URL 차단·재방문·검색 기능은 추가하지 않는다.
기존 작업·웹/문서 출처·본문 행은 변경하지 않는다.

## 구현과 결정

- `privacy_settings`의 단일 JSON 행을 엄격한 세 필드 규격으로 읽는다.
  필드 누락·잘못된 타입·지원하지 않는 차단 이름은 정상 기본값으로 해석하지 않는다.
- 설정 행이 없는 신규·기존 DB만 기존 초기값을 사용한다. 일반 실행은 수집 허용·빈 차단 목록·클립보드 꺼짐이다.
- 저장된 세 필드는 주입한 기본 정책보다 우선한다. 주입 정책은 행이 없는 DB의 초기값과 비저장 정책에 사용한다.
- 앱 생성만으로 DB를 열지 않는다. lifespan 시작과 최초 요청에서 실제 감지·수신 처리·저장 로직 전에 복원한다.
- PUT은 `BEGIN IMMEDIATE`에서 최신 행을 읽고 요청 필드만 갱신한 뒤 커밋한다.
  커밋이 성공한 뒤 전체 정책을 메모리·수집기에 적용하며 HTTP 200은 적용 이후 반환한다.
- 저장 실패는 HTTP 503으로 알리고 이전 메모리 상태를 유지한다.
  복원 실패는 원문을 보존하고 수집을 차단한다. 시작 중이면 서버가 시작되지 않으며 요청 중이면 503을 반환한다.
- 커밋 후 적용이 실패하면 목표값은 DB에 남을 수 있다. 기존 세션을 닫고 일시정지·클립보드 꺼짐으로 전환한다.
  다음 요청 또는 수집 주기에서 복원을 재시도하며, 오류로 멈춘 시간은 활성 시간에 포함하지 않는다.
- 클립보드를 켜거나 복원할 때 변경 번호 기준을 새로 잡는다. 오류 중·복원 이전의 복사를 새 작업에 붙이지 않는다.
  끄기는 OS 조회와 무관하게 즉시 적용한다.

저장 위치·요청·실패 응답의 상세 계약은 [개인정보 API](../dev/privacy-api.md#설정-저장과-복원)를 따른다.

## 검증 절차

가상 OS 감지·시계·클립보드 입력과 실제 SQLite·Backend API를 사용한다.
Client 화면 회귀 검증은 Qt offscreen으로 실행하며 데스크톱 창을 조작하지 않는다.
별도 프로세스 검증은 첫 실행 전에 일시정지를 저장하여 실제 개인 작업·복사 원문을 수집하지 않는다.

| 시나리오 | 확인 결과 |
|---|---|
| 저장된 일시정지·차단 복원 | 최초 감지·제목 읽기·브라우저 저장 이전에 적용 |
| 세 필드의 저장·새 앱/DB 재열기 | 정규화한 값과 명시적 false·빈 목록까지 유지 |
| 실제 CLI 프로세스 재시작 | 한글·공백 경로의 지정 DB에서 일시정지·차단·클립보드 설정 복원 |
| 기존 DB 마이그레이션 | 설정 테이블 없는 DB의 기존 작업 ID·내용 유지 |
| 서로 다른 필드의 갱신 | 최신 저장 행의 다른 필드를 덮어쓰지 않음 |
| 저장 오류 | 503, 이전 DB·메모리 상태 유지, 내부 오류 원문 미노출 |
| 손상·필드 누락 | 수집 시작 실패 또는 503, 기본 허용으로 초기화하지 않음 |
| 클립보드 기준점 적용 실패·복원 | 이전 복사 제외, 복원 이후 새 복사만 저장 |
| 오류 구간의 활성 시간 | 0초 시작·2초 실패·100초 복원 시 이전 기록은 2초, 새 기록은 0초 |
| 백그라운드 복원 재시도 | 추가 HTTP 요청 없이 오류 해소 후 설정 복원 |

검증 환경은 Windows 10 빌드 19045, Python 3.14.7, SQLite 3.50.4, Qt 6.12.0이다.
추가 테스트는 Backend 18개와 실제 프로세스 재시작 1개다. 이를 포함한 관련 테스트 **231 passed**,
`ruff check src tests`, `pip check`, `git diff --check`가 통과했다.
기존 Starlette/httpx 사용 중단 경고 1건이 있으며 전체 테스트를 재실행한 결과로 확대하지 않는다.

```powershell
$env:QT_QPA_PLATFORM = "offscreen"
python -m pytest -q tests/backend --ignore=tests/backend/test_health.py tests/client/test_privacy.py tests/client/test_clipboard.py tests/client/test_records.py tests/client/test_live_backend.py tests/integration/test_privacy_restart.py
python -m ruff check src tests
python -m pip check
git diff --check
```

기존 health 전용 테스트의 기본 OS 수집 경로는 이번 실행에서 제외했다.
설정 복원 실패 시 health 503과 실제 CLI 정상 준비 응답은 새 테스트에서 확인했다.

## 완료 조건과 제한

세 필드가 저장되고 새 Backend에서 수집 이전에 복원되며 실패 시 보호가 약화되지 않는 것이 이번 단계의 완료 조건이다.
Phase 5에 해당 구현·검증 체크 두 개를 추가한다. 전체 Phase는 IN_PROGRESS를 유지한다.

같은 DB에는 Backend 하나만 실행한다. 여러 인스턴스의 필드별 저장 보존 검증은
별도 프로세스 사이의 정책 실시간 동기화 지원을 의미하지 않는다.
설정 파일 복구·다중 Backend 동기화·URL 규칙은 이번 단계에 포함하지 않는다.

Python 3.11·3.12의 기존 PR #16 검증과 이번 Python 3.14 소스 검증을 구분한다.
실제 Windows·Chrome/Edge 수동 검증과 새 EXE 빌드·실행 검증은 수행하지 않았다.
기존 `b12a82a` ZIP에는 이 변경이 없으며 수정 버전 배포 전 새 패키징 검증이 필요하다.
main 병합은 보류하고 검토용 브랜치에서 관리한다.
