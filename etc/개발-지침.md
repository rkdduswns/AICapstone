# ContextTrace 개발 지침

> 본 문서는 ContextTrace 프로젝트의 디렉토리 구성, 코드 작성, 아키텍처, 테스트, Git 협업 및 문서 관리 규칙을 정의한다.  
> 팀원 모두가 동일한 기준으로 개발하기 위한 공통 참조 문서로 사용한다.

---

## 1. 기본 원칙

ContextTrace는 다음 원칙을 우선한다.

- **단순한 구조를 유지한다.**
- 필요하지 않은 디렉토리나 추상 계층을 미리 만들지 않는다.
- 기능이 실제로 필요해질 때 구조를 확장한다.
- Client, Backend, Browser의 책임을 명확히 분리한다.
- 공통 데이터 구조는 `shared`에서 관리한다.
- 실제 사용자 데이터는 저장소에 포함하지 않는다.
- 각 Phase는 작은 기능 단위로 구현하고 검증한다.
- `main` 브랜치는 항상 실행 가능한 상태를 유지한다.

## 2. 프로젝트 디렉토리 규칙

기본 디렉토리 구조는 다음과 같다.

```text
AICapstone/
├─ src/
│  ├─ client/
│  ├─ backend/
│  ├─ browser/
│  └─ shared/
│
├─ tests/
│  ├─ client/
│  ├─ backend/
│  └─ integration/
│
├─ tools/
│
├─ docs/
│  ├─ dev/
│  └─ reports/
│
├─ etc/
│  ├─ 기획-및-추상설계.md
│  ├─ 개발-지침.md
│  └─ phases/
│     ├─ README.md
│     ├─ phase1.md
│     ├─ phase2.md
│     └─ ...
│
├─ .github/
│  └─ workflows/
│
├─ .gitignore
├─ README.md
└─ pyproject.toml
```

### 최상위 디렉토리 역할

| 경로 | 역할 |
|---|---|
| `src/` | 실제 실행되는 프로그램 코드 |
| `tests/` | 단위 및 통합 테스트 |
| `tools/` | 개발 및 검증용 보조 도구 |
| `docs/` | 구현 관련 기술 문서 및 결과 보고 |
| `etc/` | 기획, Phase, 개발 규칙 등 프로젝트 관리 문서 |
| `.github/` | GitHub Actions 및 저장소 자동화 |

### 디렉토리 추가 규칙

- 새로운 최상위 디렉토리는 팀 합의 없이 추가하지 않는다.
- `client/`, `backend/` 내부는 실제 기능이 생길 때 필요한 구조만 추가한다.
- 파일 하나만 들어갈 예정인 디렉토리는 가급적 만들지 않는다.
- 동일한 책임을 가진 파일이 여러 개 생기기 시작할 때 하위 디렉토리 분리를 검토한다.
- 임시 파일이나 실험 코드는 정식 소스 디렉토리에 남기지 않는다.

## 3. 소스 영역 책임

### `src/client/`

사용자에게 직접 보이는 데스크톱 애플리케이션을 담당한다.

주요 책임:

- 검색 입력
- 검색 결과 표시
- 출처 상세보기
- 작업 타임라인
- 기록 상태 표시
- 개인정보 설정
- Backend 요청 및 응답 표시

Client는 가능한 한 **표현과 사용자 상호작용**에 집중한다.

다음 로직은 Client에 두지 않는다.

- 작업 수집 로직
- 검색 알고리즘
- 데이터 저장 로직
- 개인정보 판정 로직
- RAG 처리 로직

### `src/backend/`

ContextTrace의 핵심 비즈니스 로직을 담당한다.

주요 책임:

- Windows 작업 맥락 수집
- 작업 시간 추적
- 개인정보 보호 검사
- 작업 기록 저장
- 텍스트 처리
- 문서 처리
- 검색
- RAG
- Client 및 Browser와의 인터페이스

Backend는 UI 구현에 의존하지 않는다.

### `src/browser/`

Chrome/Edge 등 브라우저 환경에서 동작하는 기능을 담당한다.

주요 책임:

- 활성 탭 확인
- 페이지 제목 수집
- URL 수집
- 필요한 경우 페이지 텍스트 수집
- Backend로 브라우저 정보를 전달

Browser는 직접 로컬 데이터 저장소를 수정하지 않는다.

```text
Browser
  ↓
Backend
  ↓
저장 / 검색
```

형태를 유지한다.

### `src/shared/`

두 개 이상의 영역이 공통으로 사용해야 하는 데이터 정의를 관리한다.

예:

```text
ContextRecord
SearchRequest
SearchResult
SourceInfo
AppSettings
```

`shared`에는 가능한 한 비즈니스 로직을 넣지 않는다.

## 4. 아키텍처 규칙

### 기본 의존 방향

```text
Client ─────┐
            ├── Shared
Backend ────┤
            │
Browser ────┘
```

영역 간 실제 동작은 다음 흐름을 기준으로 한다.

```text
Client
  ↓
Backend API / Interface
  ↓
Backend Logic
  ↓
Data
```

```text
Browser
  ↓
Backend API / Interface
  ↓
Backend Logic
```

### 금지하는 의존 관계

다음과 같은 직접 참조는 피한다.

```text
Client → Backend 내부 구현 직접 import
Browser → 저장소 직접 접근
Client → 저장소 직접 접근
Shared → Client
Shared → Backend
```

`shared`는 다른 영역에 의존하지 않는 공통 계층으로 유지한다.

### 책임 분리

하나의 모듈은 가능한 한 하나의 명확한 책임을 가진다.

예:

```text
작업 수집
개인정보 검사
저장
검색
응답 생성
```

을 하나의 거대한 파일에 모두 구현하지 않는다.

반대로 기능이 충분히 작을 때부터 지나치게 많은 클래스와 인터페이스로 분리하지 않는다.

---

## 5. 데이터 처리 규칙

ContextTrace의 핵심 데이터는 항상 **원본 출처로 역추적 가능해야 한다.**

```text
검색 데이터
  → 작업 기록
  → URL / 파일 경로
  → 열람 시각
```

다음 정보를 임의로 분리하거나 잃지 않는다.

- 원본 작업 기록 ID
- URL 또는 파일 경로
- 프로그램 정보
- 열람 시각
- 관련 텍스트

### 개인정보 보호

민감 정보는 **저장 이후가 아니라 저장 이전에 검사**한다.

```text
수집
  ↓
개인정보 검사
  ↓
저장 허용
  ↓
저장
```

차단된 데이터가 검색 색인이나 RAG 근거에 들어가지 않도록 한다.

## 6. 코드 작성 규칙

### Python 이름 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 파일 | `snake_case` | `window_tracker.py` |
| 함수 | `snake_case` | `get_active_window()` |
| 변수 | `snake_case` | `active_window` |
| 클래스 | `PascalCase` | `ContextRecord` |
| 상수 | `UPPER_SNAKE_CASE` | `MAX_TEXT_LENGTH` |
| 비공개 내부 함수 | `_` prefix | `_normalize_title()` |

### 기본 작성 원칙

- 함수는 한 가지 역할에 집중한다.
- 지나치게 긴 함수는 역할 단위로 분리한다.
- 의미 없는 축약어를 사용하지 않는다.
- `data`, `temp`, `value` 같은 모호한 변수명은 가능한 피한다.
- 중복 코드는 공통화하되, 한 번만 사용되는 코드를 과도하게 추상화하지 않는다.
- 주석은 코드가 무엇을 하는지보다 **왜 그렇게 하는지**가 필요한 경우 작성한다.
- 사용하지 않는 코드와 주석 처리된 오래된 코드는 삭제한다.

### 타입 힌트

공개 함수와 주요 데이터 구조에는 타입 힌트를 사용하는 것을 원칙으로 한다.

```python
def get_active_window() -> WindowInfo:
    ...
```

간단한 내부 로직까지 모든 변수에 타입을 강제하지는 않는다.

### 문자열 및 경로

- 사용자 로컬 경로를 코드에 하드코딩하지 않는다.
- OS 경로는 가능한 경로 처리 기능을 통해 다룬다.
- API Key, Token, 비밀번호를 코드에 직접 작성하지 않는다.

## 7. 예외 및 로그 규칙

예외를 무시하는 코드는 작성하지 않는다.

피해야 할 형태:

```python
try:
    ...
except Exception:
    pass
```

복구 가능한 오류는 처리하고, 복구할 수 없는 오류는 상위 계층에서 알 수 있도록 전달한다.

### 로그 수준

| 수준 | 용도 |
|---|---|
| `DEBUG` | 개발 과정의 상세 상태 |
| `INFO` | 정상적인 주요 동작 |
| `WARNING` | 기능은 계속되지만 확인이 필요한 상태 |
| `ERROR` | 기능 수행 실패 |

로그에 다음 정보를 남기지 않는다.

- 비밀번호
- API Key
- Access Token
- 전체 클립보드 민감 내용
- 차단된 페이지의 본문

## 8. 테스트 규칙

기본 테스트 구조:

```text
tests/
├─ client/
├─ backend/
└─ integration/
```

### Client 테스트

UI 상태와 Backend 응답 처리 등을 확인한다.

### Backend 테스트

개별 기능의 입력과 출력을 확인한다.

예:

- 활성 창 감지
- 개인정보 필터
- 저장
- 문서 처리
- 검색
- RAG

### Integration 테스트

여러 영역이 연결되는 흐름을 확인한다.

예:

```text
작업 수집
  → 개인정보 검사
  → 저장
```

```text
검색 요청
  → Backend 검색
  → Client 결과 표시
```

### 테스트 작성 기준

- 버그를 수정할 때 가능한 경우 해당 버그를 재현하는 테스트를 추가한다.
- 외부 환경에 과도하게 의존하는 테스트는 분리한다.
- 실제 개인정보를 테스트 데이터로 사용하지 않는다.
- 테스트 데이터는 가상의 값으로 작성한다.

## 9. Git 및 협업 규칙

### `main`

`main`은 항상 실행 가능한 상태를 유지한다.

가능하면 직접 작업하지 않고 별도 브랜치에서 개발한다.

### 브랜치 이름

권장 형식:

```text
feat/<기능>
fix/<수정>
refactor/<대상>
test/<대상>
docs/<문서>
chore/<작업>
```

예:

```text
feat/window-detection
feat/browser-context
fix/privacy-filter
docs/phase-7
```

### Commit 메시지

권장 형식:

```text
feat: add active window detection
fix: prevent blocked URLs from being stored
test: add privacy filter tests
docs: update phase 7 plan
refactor: simplify context tracking
chore: update project structure
```

한 Commit에는 가능한 한 하나의 목적만 담는다.

### Pull Request

두 사람이 개발할 경우 `main` 반영 전에 상대 팀원이 확인하는 것을 기본으로 한다.

PR에서 확인할 사항:

- 변경 목적이 명확한가
- 다른 영역의 책임을 침범하지 않았는가
- 테스트가 필요한 변경인가
- 개인정보가 포함되지 않았는가
- 불필요한 파일이 추가되지 않았는가

## 10. Phase 개발 규칙

Phase 문서는 다음 경로에서 관리한다.

```text
etc/phases/
```

각 Phase는 다음 기준을 만족해야 한다.

- 한 가지 핵심 기능을 중심으로 한다.
- 완료 조건이 명확해야 한다.
- 독립적으로 테스트 가능한 결과가 있어야 한다.
- 작업량이 크면 기능을 더 작은 Phase로 나눈다.

Phase 작업 흐름:

```text
Phase 확인
  ↓
작업 분담
  ↓
인터페이스 / 공통 구조 합의
  ↓
개별 구현
  ↓
중간 통합
  ↓
테스트
  ↓
완료 조건 확인
```

Phase 완료 여부는 **코드를 작성했는가**가 아니라 **완료 조건이 실제로 동작하는가**를 기준으로 판단한다.

## 11. 문서 관리 규칙

### `etc/`

프로젝트 관리와 방향성을 위한 문서를 저장한다.

```text

├─ 개발-지침.md

포함되는 내용:

- 프로젝트 기획

- 완료 조건

### `docs/dev/`

예:

context-record-format.md
```

구현 결과와 검증 내용을 남길 필요가 있을 때 사용한다.

예:

```text

```

모든 Phase마다 보고서를 만들 필요는 없다.

## 12. 로컬 데이터 및 보안 규칙

ContextTrace는 개인 작업 정보를 다루므로 실제 실행 데이터를 Git 저장소에 포함하지 않는다.

저장소에서 제외해야 하는 예:

```text
작업 DB
사용자 URL 기록
클립보드 기록
벡터 검색 데이터
실행 로그
API Key
환경 설정 비밀값
```

실제 사용자 데이터는 프로젝트 디렉토리 외부의 애플리케이션 데이터 영역에 저장하는 것을 원칙으로 한다.

테스트에 필요한 경우 반드시 가상의 데이터를 사용한다.

## 13. 구조 변경 기준

현재 구조를 무조건 유지하는 것이 목적은 아니다.

다음 상황에서는 구조 변경을 검토한다.

- 동일 디렉토리에 서로 다른 책임의 파일이 지나치게 많아짐
- 두 영역 사이의 의존 관계가 반복적으로 복잡해짐
- 동일 기능의 코드가 여러 위치에 중복됨
- 새로운 실행 구성 요소가 독립적인 생명주기를 가지게 됨
- 테스트가 특정 기능을 찾기 어려울 정도로 복잡해짐

구조 변경 시에는 다음을 우선한다.

1. 현재 문제를 실제로 해결하는가
2. 구조가 이전보다 이해하기 쉬운가
3. 불필요한 추상 계층을 만들지 않는가
4. 두 개발자가 동일하게 이해할 수 있는가

---

## 14. 핵심 규칙 요약

1. **필요할 때 구조를 확장한다.**
2. **Client는 UI, Backend는 핵심 로직, Browser는 브라우저 연동을 담당한다.**
3. **공통 데이터 정의는 Shared에서 관리한다.**
4. **Client와 Browser는 저장소에 직접 접근하지 않는다.**
5. **모든 검색 데이터는 실제 원본 출처로 역추적 가능해야 한다.**
6. **민감 정보는 저장 전에 차단한다.**
7. **실제 사용자 데이터를 Git에 올리지 않는다.**
8. **Phase는 작은 기능 단위로 개발하고 완료 조건으로 검증한다.**
9. **main은 항상 실행 가능한 상태를 유지한다.**
