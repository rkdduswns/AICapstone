# Windows Client 배포본·네이티브 읽기 검증

작업일: 2026-11-16 (KST). 기준: `client_dev 2709a31`, 확인한 `main 7e0991e`.
작업 브랜치: `test/client-native-reading`.

## 목적·선행조건·범위

기존 EXE 진단은 연결 성공과 창 표시를 확인한 직후 종료한다. 그 결과만으로 현재 작업·보호 상태 응답이나
새 문서 읽기 화면까지 동작했다고 판단하지 않도록 검증 경계를 확장한다.
선행조건은 PR #26의 Client 읽기 흐름과 기존 Windows 빌드·실행 검증이다.

변경 범위는 Client의 선택 진단 모드, 배포 검증 도구와 관련 시험이다.
일반 실행·기존 진단 JSON·API·Backend·DB·Shared·브라우저 확장·보호 판정·의존성은 유지한다.
실제 입력기·모니터·기본 앱 조작을 자동 시험으로 완료 처리하지 않는다.

## 구현·검증 경계

1. 실행 전에 `BUILD.json`의 빌드 커밋, 실행 파일 두 개의 SHA-256, ZIP과 배포 폴더의 파일 일치를 확인한다.
   빌드 커밋과 저장소 HEAD가 다르면 저장소에 존재하는 커밋인지 확인하고 실행 코드·프로젝트 의존성·빌드 스크립트가 같은지 대조한다.
   문서/병합 커밋 차이는 허용할 수 있지만 실행 코드가 다르거나 확인할 수 없는 커밋은 통과하지 않는다.
   이는 파일 일치 검사이며 배포자 서명·신뢰성 인증을 추가하는 기능은 아니다.
   새 실행 전에 과거 성공 JSON도 비워 실패한 실행에 이전 결과가 남지 않도록 한다.
2. 새 `--smoke-test-reading`은 `--smoke-test-result`와 함께 쓰는 격리 검증용 옵션이다.
   기존 옵션만 사용하면 종전의 연결 진단과 `{ok, frozen, platform}` 결과를 유지한다.
3. 새 진단은 실제 연결·현재 작업·개인정보 상태가 모두 확인된 뒤 같은 Client 문서 탭에서 목록을 GET으로 읽는다.
   일시정지·차단이 확인된 상태도 정상 상태 수신으로 다루며 기록 허용으로 바꾸지 않는다.
4. 검증 서버에 명시적으로 준비한 연결 없는 문서 두 개를 선택하고 현재 본문 찾기·이전/다음 이동·닫기·검색 복귀를 확인한다.
   원문과 읽기 전용 속성, 원본 경로를 추정하지 않아 출처 메뉴가 비활성화되는 동작도 확인한다.
   이 진단 자체는 업로드·설정 PUT·외부 앱 열기를 하지 않는다.
5. 진단은 사용자 표시 설정을 읽거나 쓰지 않고 결과에는 불리언만 추가한다.
   원문·URL·파일 경로를 진단 JSON에 담지 않는다. 실패·시간 초과·창 닫힘은 성공으로 기록하지 않는다.

완료조건은 위 검증의 성공·실패 경계, 기존 실행 호환성과 새 Windows EXE 실행을 확인하는 것이다.

- Windows Python 3.14.7·Qt 오프스크린에서 새 읽기 진단과 실제 Client/Backend 프로세스의 HTTP, 기존 진단·표시 설정·읽기 흐름을 포함한 관련 검증 **64개 통과**를 확인했다.
- 새 진단 단위 검증은 **15개**다. health 단독 성공·상태 응답 오류·시간 초과·닫힘·늦은 응답이 성공으로 바뀌지 않으며, 다음 찾기가 실제로 이동하지 않으면 실패한다.
- 배포본 검증은 별도로 **31개 통과**를 확인했다. 같은 코드의 문서/병합 커밋은 허용하고 실행 코드·의존성·빌드 방식 차이, 손상된 식별·해시·ZIP과 이전 성공 결과의 잔존을 거부한다.
- 실제 프로세스 시험은 기존 연결 진단과 새 읽기 진단 각각의 연결 성공/실패를 확인한다. 새 읽기 성공 자료는 임시 DB에 업로드한 문서 두 건이며 사용자 자료나 표시 설정을 사용하지 않는다.
- Ruff·공백·문서 링크·14개 Phase 체크 개수 일치를 확인한다. Phase 14는 **1/28**로 유지한다.
- 최종 Windows Python 3.11·3.12 전체 검사, 새 EXE 실행과 무결성 결과 및 실제 `client_dev` 반영 SHA는 이 작업 PR의 GitHub 검사·병합 기록을 따른다.
